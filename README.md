# Instamart Customer Intelligence & Support Copilot

## Overview

This project builds an end-to-end customer intelligence and support copilot for Instamart using Python, SQLite, Machine Learning, NLP, TF-IDF Retrieval-Augmented Generation (RAG), and a simulated tool-using AI agent.

The project covers four parts:

- **Part A:** Data auditing, cleaning, SQLite database creation, SQL analysis, and RFM analysis.
- **Part B:** Customer segmentation, churn/lapse prediction, and retention prioritisation.
- **Part C:** Support ticket PII redaction, ticket classification, retry handling, and token-budget evaluation.
- **Part D:** Policy document retrieval, refund calculation, ReAct agent execution, safety limits, and checkpoint-based recovery.

The project uses the supplied `generate_data.py` and `mock_llm.py`. The LLM interactions are simulated locally; no external API key is required.

### Task 2 – TF-IDF retrieval

A TF-IDF index was built using `TfidfVectorizer()` and cosine similarity.

The retrieval function returns the top matching chunks with their source filename, similarity score, and text.

The query `refund policy late delivery` returned three chunks from `refund_policy.txt`.

TF-IDF uses term frequency and inverse document frequency to represent text. It is based on word overlap and may not recognise synonyms as effectively as embedding-based semantic retrieval.

### Task 5 – Refund tools

The refund agent uses five tools:

1. `get_order` – retrieves order details from SQLite.
2. `search_policy` – retrieves relevant policy chunks.
3. `calculate_refund` – calculates the eligible refund amount.
4. `issue_refund` – records an approved simulated refund.
5. `escalate_to_human` – records a refund requiring human review.

Refund rules:

- Only completed orders are eligible.
- Delivery taking more than 45 minutes qualifies for a full order-amount refund.
- Delivery taking 45 minutes or less qualifies for no refund.
- Refunds above INR 1,000 must be escalated to a human.
- Refund actions are simulated and recorded locally; no real payment is processed.

### Task 9 – ReAct vs Plan-and-Execute

ReAct performs reasoning and tool execution step by step, using each tool observation to decide the next action. In the measured ReAct runs, S1 used 5 model calls and 1,322 tokens, S5 used 3 calls and 592 tokens, and S6 used 2 calls and 242 tokens.

Plan-and-Execute creates a sequence of actions before carrying them out. This can make execution more structured, but an unexpected tool observation may require replanning. ReAct is more adaptive because it incorporates each observation before selecting the next tool.

For this refund workflow, ReAct is suitable because the agent must inspect order status, retrieve policy information, calculate the refund, and decide whether to issue or escalate it. The measured results above are from ReAct; a separate Plan-and-Execute benchmark was not run.

## Limitations and Next Steps

### Limitations

- The supplied mock LLM simulates model behaviour and is not a live production LLM.
- TF-IDF retrieval relies on word matching and has limitations with synonyms and semantic similarity.
- Refund processing is simulated using a local JSONL ledger; no real payment gateway is connected.
- The retention prioritisation output is illustrative and requires further validation before production use.
- The project uses a generated dataset and should be tested with real-world data before deployment.

### Next Steps

- Evaluate embedding-based semantic retrieval against TF-IDF.
- Add more policy evaluation questions and edge cases.
- Test the agent with additional order and refund scenarios.
- Integrate an authenticated production LLM and real payment workflow only with appropriate safeguards.
- Monitor model accuracy, token usage, latency, and human escalation rates.
- Improve the retention model using time-based validation and leakage checks.
